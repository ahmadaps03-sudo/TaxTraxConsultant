# Client Portal data integration (shared Dev)

The three `20261011000*` Client Portal migrations are already recorded in shared Supabase Dev. Do not reapply or edit them. The forward-only `20261012000100_client_portal_security.sql` migration must be reviewed and applied to **Dev only** before enabling e-signatures or document uploads. It removes client-provided e-sign audit fields, verifies document size/MIME against the stored object, and tightens direct Storage insert/delete paths. Production is not configured by this work.

The website uses its existing `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`, `AUTH_ORIGIN`, and `ADMIN_API_KEY`. Client APIs use request-scoped user sessions and RLS. The staff API additionally needs `ADMIN_PORTAL_SECRET` in the website's untracked `.env.local` and as an Edge Function secret; use the **same new random value** on both sides, distinct from `ADMIN_API_KEY`, `ADMIN_ACCESS_REQUEST_SECRET`, and `ACCESS_REQUEST_SUBMISSION_SECRET`. Never place it in renderer code or Git. `portal-admin` must be deployed to shared Dev with JWT verification disabled; the function verifies its scoped Bearer secret and holds the Supabase service-role credential only in Supabase Edge. The desktop app continues to send only its existing `x-admin-key` to the local website backend.

The `client-documents` Storage bucket must remain private. Before allowing sensitive uploads, verify the Dev bucket, effective `storage.objects` policies (including any policies not created by these migrations), and direct Storage API behavior with two synthetic clients. The local Supabase configuration disables Storage, so local SQL tests alone do not cover it.

The portal overview optionally displays appointments from the existing SQLite bookings store by email. A missing/unavailable SQLite bookings store yields an empty appointments list; all new portal data remains in Supabase. This is transitional and must not be treated as a migrated bookings feature.

Manual QA uses synthetic Dev identities only: log in as active client A, check every tab and allowed actions, verify client B cannot access A's API objects or Storage paths, suspend A and verify access is denied, then verify logout/revocation. For staff actions, start the website backend with the server-only secret and use the existing admin key; confirm requests without it fail. Do not use real tax or financial documents during QA.
