# Vercel staging prerequisites

This is a preparation checklist, **not** a deployment or Production approval.
Use Node 22.19.0 and set the Vercel project root to `website/`.

- Choose and verify the **staging** Supabase project. Apply the repository migrations and deploy the current `site-persistence`, `submit-access-request`, `review-access-requests`, `portal-admin`, and email functions to that project. The updated request/review/admin functions use their own Supabase project's `SUPABASE_URL`, not a hardcoded Dev ref. These target-agnostic function versions are not yet deployed to any project (shared Dev still runs the earlier Dev-pinned versions). Set the review function's `AUTH_ORIGIN` secret to the exact staging website origin before inviting anyone; without it invitations fail closed. Keep the Auth redirect allowlists and email-hook origin allowlists (`RECOVERY_ALLOWED_ORIGINS`, `ACTIVATION_ALLOWED_ORIGINS`) in sync.
- Configure website server values privately: `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`, `AUTH_ORIGIN`, `ADMIN_API_KEY`, `ADMIN_PORTAL_SECRET`, `ADMIN_ACCESS_REQUEST_SECRET`, `ACCESS_REQUEST_SUBMISSION_SECRET`, `SITE_INGEST_SECRET`, `SITE_ADMIN_DATA_SECRET`, `WELCOME_EMAIL_SECRET`; set `NEXT_PUBLIC_SITE_URL` to the staging site **before the build** (it is inlined at build time; when unset, canonical/sitemap URLs fall back to the public production domain). `ANALYTICS_SALT` (falls back to `SITE_INGEST_SECRET`) and `NEXT_PUBLIC_WHATSAPP_NUMBER` are optional. Set each scoped Edge secret in the matching staging project: `SITE_INGEST_SECRET`, `SITE_ADMIN_DATA_SECRET`, `ACCESS_REQUEST_SUBMISSION_SECRET`, `ADMIN_ACCESS_REQUEST_SECRET`, `ADMIN_PORTAL_SECRET`, `AUTH_ORIGIN`, and the email hook's `SEND_EMAIL_HOOK_SECRET`, `EMAILJS_*`, `RECOVERY_ALLOWED_ORIGINS`, `ACTIVATION_ALLOWED_ORIGINS`. `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` are provided to Edge Functions by Supabase. Never add service-role credentials to Vercel, browser code, Electron or Git.
- Keep `TRUST_PROXY` unset for the first staging deployment. This ignores caller-supplied forwarding headers and gives public routes one conservative `unknown` rate-limit bucket, so limits apply site-wide rather than per visitor (for example 5 contact messages and 8 bookings per 10 minutes for the whole site, observed during local QA). Analytics country is then always `ZZ`. Vercel documents `x-vercel-forwarded-for` as its ingress-provided client IP and `x-forwarded-for` as normally overwritten, but verify the actual staging ingress/proxy chain before enabling per-IP trust. Do not set `TRUST_PROXY=1` behind an unverified upstream proxy. When enabled, analytics country also trusts `cf-ipcountry` and similar headers ahead of `x-vercel-ip-country`; a caller can spoof those on Vercel, which affects analytics country only. Resolve this per-visitor limiting decision before real public traffic.
- Keep `client-documents` private. Verify the existing bucket's 25 MB and MIME limits, owner-path Storage policies, signed upload, metadata attachment, signed download, deletion and two-client isolation with synthetic files only. The new browser upload path does not send a 25 MB body through a Vercel Function. Review orphaned unregistered objects after interrupted uploads; the browser cleanup is best-effort.
- The guarded daily GitHub Actions workflow `staging-telemetry-prune.yml` is inert until the owner sets `STAGING_TELEMETRY_PRUNE_ENABLED=1` and the staging `STAGING_SUPABASE_REF`, `STAGING_SUPABASE_URL`, `STAGING_SUPABASE_PUBLISHABLE_KEY` variables plus `STAGING_SITE_ADMIN_DATA_SECRET` secret. Confirm the ref is **not Production** before enabling it. The script validates the exact configured project URL and invokes the existing service-only prune capability; no database password or service-role key enters GitHub. Scheduled workflows run from the repository default branch, so enable only after approved integration.
- Run synthetic manual QA from `TESTING.md` for login/logout, access requests, Admin APIs, portal documents and analytics. Point Electron Admin to the staging website URL with its existing `x-admin-key`; no renderer/API contract change is required.

Legacy local SQLite files are retained privately as backup/reference data. They are not imported to staging or read by website runtime. No Production environment is touched by this checklist.
